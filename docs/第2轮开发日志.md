# 第 2 轮开发日志：Trace Agent 诊断闭环

## 1. 本轮目标

本轮目标是让 Codex 或兼容 Agent Harness 接收自然语言 Trace 问题，自主选择本地 Trace MCP Tool，并稳定输出“现象判断、关键证据、不确定项、下一步建议”。范围严格限定为 BLF 与可选 DBC/ARXML 中实际发生的现象，不实现完整根因定位或多智能体编排。

用户在开发中明确调整了实现约束：不得创建或使用 API Key，不使用 OpenAI API、`openai-agents` 或独立模型调用。模型推理由 Harness 提供，Trace Agent 必须使用 Harness 原生能力。

## 2. 上一轮基础

本轮基于提交 `c5933c86abf0258f4413ccb3197575a90d8a12a8`。上一轮已经完成 Trace Core、进程内 Session、BLF 读取、DBC/ARXML 基础加载、报文查询、时序统计、信号解码及 5 个 Trace MCP Tool。本轮没有重写这些稳定能力。

## 3. Trace Agent 最终设计

最终采用最小的 Harness 原生结构：

~~~text
Codex / 兼容 Harness
  ├─ .agents/skills/trace-analysis/SKILL.md
  └─ .codex/config.toml
          ↓
     本地 automotive-trace stdio MCP
          ↓
     TraceSessionManager
          ↓
现象判断 / 关键证据 / 不确定项 / 下一步建议
~~~

项目没有 Python Agent 运行时。原 `src/anda/agents/trace_agent.py` 是 Agents SDK TODO 占位，已删除；`pyproject.toml` 中的 `openai-agents` 可选依赖也已移除。根目录旧 `skills/` 草案目录不属于 Codex 的项目 Skill 原生发现路径，因此一并删除，避免双份规则漂移。

没有新增项目 `AGENTS.md`。该文件更适合所有任务都要遵循的工程规则，而 Trace 调查是按语义触发的专业流程，放入项目 Skill 更精确。没有使用子智能体或多智能体编排。

## 4. Agent Prompt / Skill 思路

`trace-analysis` 的 frontmatter 描述同时承担发现和触发职责，正文只包含领域调查所需的长期规则：

- 从问题提取 BLF、数据库、CAN ID、Channel、信号和时间范围；
- 按问题类型选择最短 Tool 路径；
- 保持时间范围、Channel 与 `trace_id` 一致；
- 只使用 Tool 结果形成事实；
- 明确禁止越界推断配置、源码、ECU、硬件和 CANoe 根因；
- 回答问题后立即停止。

Skill 与底层 Tool 职责分离：Skill 决定“为何查、先查什么、何时停止”，MCP 负责“确定性地查什么”。

## 5. Tool 调用策略

- 报文存在性：`load_trace → find_messages`。
- 指定 Channel 缺失：只有首次结果为零时，才用相同 CAN ID 和相同时间范围再查一次不限 Channel。
- 时序问题：`load_trace → get_message_timing`；只有需要定位关键时间点才补 `find_messages`。
- 信号问题：有数据库时 `load_trace → search_database → decode_signal`；无数据库时不猜 CAN ID，也不做无意义日志加载。
- 整体概览：只有用户确实询问全局范围、帧数、Channel 或 CAN/CAN FD 构成时才用 `get_trace_summary`。

同一调查只加载一次输入，后续复用 `trace_id`。默认帧/信号样本 `limit=20`。

## 6. Structured Output 设计

当前 Harness 原生 Skill 没有项目内可强制执行的 Pydantic structured output 边界，因此没有为测试而增加一个无人消费的 Python模型。Skill 通过固定 Markdown 二级标题提供稳定契约：

1. 现象判断；
2. 关键证据；
3. 不确定项；
4. 下一步建议。

顺序与标题文字固定，每节至少一条；无证据时明确写“暂无”或“基于当前证据无法确认”。该格式既适合当前会话阅读，也便于未来上层 Agent 做轻量解析。

## 7. 是否新增 Trace MCP Tool

新增 1 个 Tool：`search_database(trace_id, query, limit=20)`。

它按 Message 或 Signal 名搜索当前 Session 已加载的 DBC/ARXML，返回有限的 CAN ID、Message 名、匹配 Signal 名及精确匹配标记。结果最多 20 项，不返回整个数据库，不做诊断。

## 8. 新增 Tool 的原因

原有 `decode_signal` 要求调用者已经知道 CAN ID。用户只问“VehicleSpeed 的变化如何”时，Harness 无法从信号名确定所属报文，闭环会在解码前中断。因此需要一个纯数据库导航 Tool。

实现保持 MCP 层薄：`server.py` 只转发参数；搜索逻辑位于 `NetworkDatabase`；Session 层负责数据库存在性、输入校验、上限和返回契约。上一轮 5 个 Tool 的参数与行为未改变。

## 9. 调查流程示例

问题“为什么 CAN2 上看不到 0x100？”的最短流程：

~~~text
load_trace
  ↓
find_messages(0x100, CAN2, limit=20)
  ↓ 仅当 0 条
find_messages(0x100, 不限 Channel, 相同时间范围, limit=20)
  ↓
报告 CAN2 未观察到及其他 Channel 的客观证据
  ↓
不推断 PduR、ECU 或硬件根因
~~~

问题“VehicleSpeed 如何变化？”的最短流程：

~~~text
load_trace(BLF, DBC)
  ↓
search_database(VehicleSpeed)
  ↓ 唯一精确匹配
decode_signal(候选 CAN ID, 数据库规范信号名, limit=20)
~~~

## 10. Token / Context 控制措施

- 不例行调用所有 Tool；
- 不重复 `load_trace`；
- 精确 CAN ID 问题不先取全局摘要；
- 时序问题优先统计而不是先拉 200 帧；
- 默认样本上限 20，服务端原有硬上限 200 保持不变；
- 数据库导航最多返回 20 个轻量候选；
- 最终回答只摘录关键计数、时序统计和少量样本，不复述完整 Tool 返回。

## 11. 测试 Case

`evals/trace_agent_cases.json` 固化 6 个行为场景：

1. 0x100 在 CAN1 存在；
2. 0x100 在 CAN2 缺失并按条件跨 Channel 回查；
3. 0x200 时序分析；
4. VehicleSpeed 搜索并解码；
5. 没有 DBC 时拒绝猜测信号映射；
6. Trace 只能证明现象时不虚构 PduR 根因。

确定性测试验证项目 Skill 位置/frontmatter、最短路径指令、固定四段输出、证据边界、项目 MCP 配置、无独立模型依赖、数据库搜索上限、缺失数据库与非法输入错误，以及 FastMCP 真实调用。

## 12. 真实 Agent 验证结果

真实验收使用本机 Codex 的 ChatGPT 登录态与云端模型，没有 API Key。自然语言问题触发后，模型自动选择了项目 `trace-analysis` Skill，并规划 `load_trace → find_messages(CAN2) → 条件性 find_messages(不限 Channel)`。通过项目 PowerShell 启动器连接本地合成 BLF 后，实际结果为 CAN2 0 帧、CAN1 4 帧，调用顺序与 Skill 一致。

`codex mcp list` 能发现并启用项目 `automotive-trace` 配置；独立的 stdio 启动器测试能列出全部 6 个 Tool。当前 Codex CLI 新建的只读验收会话没有把项目 MCP Tool 注入模型原生工具清单，因此模型在首次验收中通过本地 MCP Client 完成调用，而不是直接生成原生 MCP Tool Call。按照用户允许的兜底方式，本轮用确定性 Skill/配置/MCP 测试补足自动化验证；不能把原生绑定写成已通过。

云端 WebSocket 在本机通常重试 5 次后回退 HTTPS，这是当前网络的正常行为。一次临时代理尝试未成功且未写入项目；公共配置不依赖任何代理。

## 13. Code Review 发现

使用 Codex 原生 `codex review --uncommitted` 独立审查。Review 发现：

- 跨 Channel 回查没有明确要求保留用户时间范围，可能混入范围外证据；
- 大小写不一致的信号查询虽然能搜索成功，但若继续使用用户原始拼写会在大小写敏感解码中失败；
- 人工验收生成的临时 DBC/BLF 必须在提交前删除。

Review 过程中直接运行 pytest 受沙箱临时目录与环境中 `pytest-qt` 自动插件影响而报权限错误；这不是业务测试失败，最终回归使用项目既定的隔离参数完成。

## 14. Review 修复

- 明确要求指定 Channel 查询与跨 Channel 回查使用完全相同的时间范围；
- 明确要求 `decode_signal` 使用 `search_database.matches[].matched_signal_names` 返回的数据库规范信号名；
- 增加大小写变体搜索测试和对应 Skill 契约断言；
- PowerShell 启动器固定 stdin/stdout 与 Python 为 UTF-8，避免 FastMCP stderr 在中文 Windows 上影响 Harness 初始化；
- 提交前清理所有合成验收文件和 pytest 临时目录。

## 15. 最终回归

Review 修复后定向测试：18 passed。最终完整回归：31 passed。`ruff check src tests` 通过；Skill Creator 的 `quick_validate.py` 校验通过；真实 PowerShell stdio 启动器测试通过。

## 16. 当前限制

- 当前 Harness 版本能发现项目 Skill 和项目 MCP 配置，但新建 CLI 验收会话未把项目 MCP Tool 原生注入模型工具清单；需要后续在支持项目 MCP 原生绑定/重载的 Harness 版本复验。
- Trace Session 与 MCP 进程同生命周期，服务重启后需要重新加载 BLF。
- 信号调查必须提供 DBC/ARXML；数据库不存在或存在多个精确候选时 Agent 不会猜测。
- 没有 expected period、容差或功能规格时，只能报告客观时序/数值现象。
- 当前仍不具备 Config、CANoe、源码、硬件或自动完整根因定位能力。
