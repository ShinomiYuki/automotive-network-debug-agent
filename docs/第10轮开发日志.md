# 第 10 轮开发日志：TSMaster MCP 一期

日期：2026-10-22

## 本轮目标与交付边界

为外部实体域控板的 CAN 路由测试增加独立 TSMaster MCP。源侧发送明确、有限的刺激，目标侧记录实际接收帧；测量日志停止写入后，按明确需求检查整帧、信号和诊断帧路由。

本轮交付代码、模拟接口和合成 BLF/DBC 验证、使用说明、配置示例及手动台架步骤。本机旧版库在通道配置阶段返回错误 82，用户已明确确认先交付代码与离线验证并记录该阻碍。本轮未连接真实设备、发送报文或进行域控板验收。

## 独立服务和控制流程

新增 `anda.mcp.tsmaster.server`，注册独立 `automotive-tsmaster` 服务，提供八个工具：

- `get_tsmaster_health`
- `create_tsmaster_session`
- `get_tsmaster_status`
- `run_tsmaster_test`
- `stop_tsmaster_test`
- `close_tsmaster_session`
- `analyze_tsmaster_log`
- `get_tsmaster_result`

原有 CANoe 26 项工具契约保持不变。TSMaster 使用 `TSMaster.TSApplication` 进程外 COM，不使用进程内入口，不加载 x86 原生 DLL，不采用本机缺失的新版本 RPC，也未引入跨位数工作进程或通用供应商框架。

每个服务进程同时只允许一个独立工程。启动前检查进程及 COM 活动对象；发现已有实例或无法确认唯一所有权时拒绝操作。所有 COM 调用固定在同一工作线程。应用启动授权与本次连接、发送授权分开，均默认关闭。

工程流程包含新建或加载已审核模板、指定 `.T7z` 保存、回载、硬件映射读回及 DBC 文件集合检查。速率实际读回及 DBC 通道归属保留为人工核对项，不把配置调用无异常当成已核对。真实参数必须明确提供，不使用示例值猜测台架。

## 有限刺激、回放和记录

指定帧发送限制数量、间隔和总时限，校验标准或扩展标识符、经典 CAN 或 CAN FD、BRS 和合法数据长度。FD 数据长度转换为 DLC 编码。目标口不允许普通刺激；明确的诊断模拟响应通过单独的用途和批准标识符记录。

回放先从输入 BLF 筛出明确源通道、批准标识符、原日志方向和时间片段，再写入独立刺激 BLF。历史目标输出不会进入发送计划。超过帧数上限、选中不支持的帧或空选择时拒绝执行，并移除本次未审核完成的输出文件。

原 BLF 通道、逻辑通道、物理端口和 DBC 绑定分别建模。在线回放映射使用一基目标通道，零表示忽略；硬件、结构和数据库参数在调用边界转换为零基。原日志 Rx 可作为批准刺激，不能固定只选择 Tx。

记录在刺激前开始，先保留基线，刺激结束后保留完整响应窗口，再停止回放、停止记录和断开。接收事件只用于有限反馈；权威判定读取关闭的新 BLF。回放状态、配置读回和清理结果分别记录，进度 100% 不能代替完成状态或路由判定。

执行支持取消、超时和异常后的清理。厂商 COM 调用若阻塞，取消仅提交标志，不能保证即时中断；待完成和关闭失败状态会保留。正常关闭未完成时报告仍存在的自有进程，不伪报已关闭，也不强制终止用户实例。MCP 生命周期结束时提交会话清理。

## 完整日志检查和报告

复用 Trace BLF 读取与数据库解码，新增完整日志的方向、通道、标识符、帧类型和时间窗口关联。目标必须为接收方向，错误帧不会成为合格证据；源刺激必须在本次日志中可见。基础检查不默认比较全部数据。

内部分析全部帧。每条用例的匹配对、源帧和目标帧证据各最多返回十条，保留一基原始帧序号、时间、通道、方向、数据、帧类型和信号值。完整计数不会受证据数量上限影响。状态查询返回摘要，结果工具按用例分页，完整 JSON 报告包含输入用例、台架配置、发送计划、环境、错误、清理结果和分析证据。

结果区分观察到预期转发、窗口内未观察到、证据不足和未执行。源刺激缺失、采集完整性未确认、方向或时钟未确认、通道不完整、背景同标识符流量或解码异常均不能默认为通过。失败只描述观察结果，不直接推断域控软件根因。

信号检查要求两端 DBC、网络、通道、信号、线性转换和容差明确，解码目标实际接收帧，按窗口内最新源值检查。诊断请求正向和明确响应反向分别建用例；真实 ECU 响应需额外来源确认。结果明确未检查完整 ISO-TP/UDS 事务，不以历史响应或流控证明本次服务完成。

当前公共 Trace 模型未保留远程请求标记。分析需要明确的数据帧范围确认，缺少确认时返回证据不足；发送和刺激筛选会直接拒绝远程请求帧。

## 本机执行证据

使用用户指定的 Miniconda 环境 `DaVinci-GW`，Python 3.12.14、64 位。项目依赖和 pywin32 可导入。本机 TSMaster 为 2023.3.21.848、32 位。

已实际验证 COM 注册检查、无既有实例时创建独立进程、取得 COM 子接口、空白工程新建、指定 `.T7z` 保存、产物存在、再次加载及正常关闭请求。旧版关闭时出现过保存提示，后端只处理已确认属于本会话的保存提示，并保留关闭失败状态。

最小 `set_can_channel_count(2)` 在尚未导入 DBC、配置硬件或连接总线时返回 `OLE error FFFFFFAE`，错误码 82，描述为 `libTSMaster generic operation failed`。在安装目录作为工作目录的最小尝试中也出现同一失败。当前没有证据证明具体根因；未修改第三方安装文件、注册表或驱动，没有用额外原生 SDK 上下文规避该问题。

用户提供的真实参考 BLF 可完整读取，共 8185 个 CAN/CAN FD 帧，覆盖 11 个记录通道；其中经典 CAN Tx 6209 帧、CAN FD Rx 1552 帧、经典 CAN Rx 424 帧。其可读取 CAN 帧时间跨度约 0.600 秒，顺序正常。文件头显示由 CANoe 记录，因此这只验证参考 BLF 读取兼容性，不证明 TSMaster 新日志格式已台架通过。没有根据文件名推断网络绑定，也没有用该历史日志声称本次路由通过。

本机参考日志摘要保存在 `output/tsmaster-offline-probe/reference-blf-compatibility.json`；空白工程产物保存在同目录。真实日志未复制到发布示例或测试夹具。

## 测试和检查

最终完整回归：`157 passed, 3 skipped in 35.67s`。三项跳过为默认关闭的两项 CANoe 实机测试和一项 TSMaster 离线 COM 测试。四个 MCP 的 PowerShell 启动器均经过真实标准输入输出客户端连接及工具列表验证。

确定性验证覆盖源回放隔离、旧 Rx 刺激、零基与一基转换、COM void 与输出参数、FD DLC、源目标方向和帧类型、有限发送、停止、超时、异常清理、超过 200 帧后的匹配、完整计数与有限证据、DBC 歧义与转换、诊断两个方向及事务边界。

显式启用的 `tests/integration/test_tsmaster_com_offline.py` 在本机执行过，实际结果为通道配置错误 82，未记为通过。默认回归不会激活 TSMaster 或连接硬件。

新增输入模型触发了既有 CANoe 清理代码的共存问题：全局对象扫描访问 Pydantic 内部对象时可能抛出运行错误。仅在扫描无关对象的两处属性检查中跳过该异常，并增加共存回归，未改变 CANoe 工具契约或其他行为。

Ruff 检查、格式检查、发布清单 JSON、示例模型及用例校验、`git diff --check` 通过。回归使用现有 `ANDA_CACHE_DIR` 和本次临时目录，避免沙箱外缓存权限影响验证。

当前可用原生代码审查工具只提供拉取请求检查，未提供适用于本地工作区变更的审查入口。本轮未伪造原生审查结果，也未创建提交或拉取请求。
