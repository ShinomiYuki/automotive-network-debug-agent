# 第 8 轮开发日志：Dynamic Verification Core

日期：2026-09-15

## 本轮目标

在现有单一 Codex Plugin 中增加第三个本地 MCP `automotive-dynamic`，把 CANoe
动态验证做成可由 Harness 直接调用的确定性工具层。本轮不新增 Dynamic Skill/Agent，
不修改 Debug Skill 的 Trace/Config 编排，不创建模型运行时，也不使用
`OPENAI_API_KEY` 或 OpenAI API。

## 参考实现取舍

本轮对照了仓库内三份本地参考：

- `samples/py-canoe-main`：采用其 CANoe COM 对象模型和 `py-canoe` 调用方式；
- `samples/CANoe-mcp-main`：参考连接、Signal、Replay、Logging、Diagnostic 与 Test
  能力划分，但没有复制其无状态连接模型；
- `samples/canoe-mcp-debugger-main`：采用“一个 MCP 生命周期内持有同一 COM Session”
  的原则，并确认任意 CAN 帧发送应通过配置内 CAPL Bridge。

最终实现保持项目原有 FastMCP、统一错误模型和 Trace Core，不引入新的模型 Provider、
独立 Agent SDK 或额外运行时抽象。

## 已实现内容

### Stateful Dynamic Core

- 一个 Dynamic MCP 进程最多维护一个活动 Session；
- 所有 CANoe COM 创建与调用固定在单个后台 worker 线程；
- BLF-only 创建工作区外临时 CANoe 配置；
- 用户提供 `.cfg` 时创建同目录影子副本，关闭时重新计算原文件摘要；
- `auto` 固定解析为 offline，不根据环境猜测 online；
- Session 关闭时停止活动操作、退出 CANoe、删除影子配置和临时目录，并返回清理结果；
- BLF 时间窗查询直接复用 Trace Core，不进行 MCP-to-MCP 调用。

### 26 个 Dynamic Tool

会话与构建：`get_dynamic_health`、`create_dynamic_session`、
`get_dynamic_status`、`close_dynamic_session`、`compile_capl`。

控制与等待：`control_measurement`、`control_offline_animation`、
`wait_runtime_event`。

观察：`observe_bus_window`、`get_signal`、`get_variable`、
`read_write_window`、`get_bus_statistics`、`inspect_network_model`、
`get_debug_snapshot`。

运行时修改与主动操作：`set_signal`、`set_variable`、`call_capl_function`、
`transmit_can_frame`、`send_diagnostic_request`。

Replay、Logging 与 Test：`configure_replay`、`control_replay`、
`manage_logging`、`list_tests`、`start_test`、`get_test_result`。

### 副作用与运行策略

每个 Tool 都带有 `READ_ONLY`、`LOCAL_MUTATION`、`RUNTIME_MUTATION` 或
`BUS_ACTIVE` 元数据。默认 runtime policy 只开放 observation、offline_animation
和 measurement；Signal/Variable 写入、CAPL、Replay、帧注入、诊断、测试与 Logging
必须在创建 Session 时显式授权。

原始帧注入在 Core 中限制 CAN ID、Classic CAN/CAN FD 载荷长度、帧数、重复间隔和
总时长。实际发送依赖配置内的
`ANDA_TransmitCanFrame(channel, arbitrationId, flags, dataHex)` CAPL
函数；Bridge 不存在时返回“不支持”，不会隐式修改用户工程。

### Offline Source 与 Replay

BLF 离线播放只进入 CANoe Offline Source，并由 Offline Animation 控制。Replay Tool
只操作明确命名的 Replay Block。两者使用不同的接口和状态，不把 Replay 当作离线播放
的替代实现。offline Session 中普通 Measurement Start/Reset 被拒绝，避免旧版 CANoe
在模式无法确认时访问真实总线。

### 一键能力采集

增加 `scripts/collect_dynamic_capabilities.ps1`。它可以在只能访问公司许可证、无法连接
Codex 的内网环境中独立运行，将结构化 JSON 写到用户目录。采集器只创建最小临时配置
和合成 BLF，执行安全离线能力检查；不会发送原始帧、诊断请求或启动 Replay。Python
进程退出后，脚本会按固定目录名前缀校验并重试删除本次临时目录。

## CANoe 14 实机验收

验收环境：

- `Vector CANoe.CAN.LIN /pro 14.4.13`；
- CANoe 14 SP4；
- `py-canoe==26.4.1`；
- Python 3.12，复用现有 Conda 环境。

安全离线验收已确认：

- 许可证不是 View Only，CANoe COM 可正常创建；
- 临时配置保存成功；
- 模式强制为 offline 并完成回读；
- 合成 BLF 成功加入 Offline Source；
- CAPL 编译结果为 0；
- Offline Animation 的 start、pause、step、resume、reset、stop 均成功；
- `measurement_started` COM 事件等待成功；
- CANoe 正常退出，探测临时目录清理成功。

空白临时配置的能力清单还确认：Replay Collection、Test Environment、Diagnostic 与
Logging Collection 可访问，但没有可执行的测试、诊断 ECU 或 Replay Block；CAN1 Bus
Statistics 在该空白配置中不可用；`ANDA_TransmitCanFrame` Bridge 不存在，因此没有
发送任何帧。这些结果按“当前配置不支持”保留，不伪造成功。

## 兼容性修复

CANoe 14 生成的 win32com wrapper 暴露小写 `mode` 属性，而 `py-canoe==26.4.1`
访问大写 `Mode`。适配器现在先探测实际属性名并直接完成设置与回读；值 `0` 表示 online，
值 `1` 表示 offline。

另一个兼容点是 CANoe 14 SP4 的 `Application.Version.Minor` 为 `4`，但 `SaveAs` 的
目标文件格式版本需要 `14.0`，不能写成 `14.4`。临时配置现在使用当前 Major 和 Minor
`0` 保存，已通过实机验证。

## 测试与边界

新增确定性测试覆盖：默认策略、单 Session、同线程 COM 调用、影子配置和原文件保护、
帧注入上限、Trace Core 复用，以及 Dynamic MCP 恰好暴露 26 个 Tool 与正确副作用注解。
最终 `ruff check --no-cache` 通过，完整测试为 `86 passed`，其中 stdio 启动器测试实际
连接 Trace、Config、Dynamic 三个独立 MCP 并核对各自 Tool 集合。

本轮没有使用真实业务 `.cfg` 做在线总线主动操作，因此以下能力仍由具体 CANoe 配置决定：
Signal/Variable 可写性、CAPL 函数、Replay Block、Diagnostic ECU、Logging Block、Test
Module、Bus Statistics 和 Network Model 内容。后续实机验收应使用专门的受控测试配置，
不应直接对量产工程或真实车辆开放 `BUS_ACTIVE` policy。
