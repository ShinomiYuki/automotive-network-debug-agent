# 第 6 轮开发日志：大型输入异步加载与 LIN/LDF

## 1. 本轮目标

修复真实大 BLF、工程源码和大型 ARXML 在 MCP Tool 超时前无法返回 ID、重试后重复高成本索引的问题；同时补齐 BLF 中 LIN 帧与 LDF 数据库的确定性查询能力。本轮真实数据仅用于验证插件加载和查询能力，不分析具体超时现象或故障根因。

## 2. 开发前现状与问题定位

- `load_trace` 完整扫描 BLF 并建立内存索引后才返回 `trace_id`；623.5 MB 真实 BLF 的工作时间明显超过原 60 秒 Tool 超时。
- `load_config_workspace` 完整扫描工程、解析 ARXML 并建立源码索引后才返回 `workspace_id`。
- Harness 超时重试会启动新的加载，无法复用仍在进行的工作。
- Trace Reader 基于 python-can，只返回 CAN/CAN FD；数据库仅支持 DBC/ARXML，无法查询 BLF 中的 LIN 记录或使用 LDF 解码。
- 本机大量 `davinci-gw-mcp.exe` 并非本插件启动器产生。排查时用户级 Codex 配置仍启用了旧的 PyInstaller 单文件 MCP；Codex 任务初始化会自动启动它，每个实例表现为父/子两个同名进程并创建 `_MEI*` 解包目录。

## 3. 最终设计

```text
load_trace / load_config_workspace
          │  校验输入、按文件身份去重
          ▼
立即返回稳定 trace_id / workspace_id
          │
          ▼
进程内单槽 daemon worker 建立索引
          │
          ▼
get_*_load_status(wait_seconds <= 55)
          │
          ▼
ready 后复用同一 ID 查询
```

Load Tool 不再等待重型索引完成。相同输入处于 `queued/loading` 时再次 Load 只返回同一 ID 和 `reused=true`；Trace 与 Config 分别最多运行一个重型构建，避免同一 MCP 进程内并发堆积大型索引。状态锁不覆盖文件扫描和 XML/BLF 解析，因此状态查询与其他 Load 请求不会被重型工作长期占用。

同步 Core 方法保留，供确定性单元测试和非 MCP 调用者使用；只有 MCP Load Tool 改用后台入口。索引仍保存在当前 MCP 进程内，不生成大型磁盘缓存。后台线程使用 daemon 生命周期，stdio 断开后不会以非守护线程阻止进程退出。

## 4. Trace Core 数据流

```text
Vector BLF
  └─ vblf 容器读取与选择性对象解包
       ├─ CAN_MESSAGE / CAN_MESSAGE2
       ├─ CAN_FD_MESSAGE / CAN_FD_MESSAGE_64
       └─ LIN_MESSAGE / LIN_MESSAGE2
              ↓
        bus-aware RawFrame
              ↓
        CompactFrameStore
              ↓
  CAN/LIN 查询、时序统计、DBC/ARXML/LDF 解码
```

Reader 只解包调查需要的 CAN、CAN FD、LIN 和错误帧对象，跳过 AppText 等无关对象。这样既减少大型日志的对象构造，也避免无关文本编码异常阻断总线帧索引。BLF 中的 Vector 1-based Channel 原样对外返回。

vblf 0.3.1 对旧 `CAN_FD_MESSAGE` 的结构尺寸与 python-can 4.6.1 生成的 116 字节对象不一致，因此增加了一个局部兼容解包器，严格按 Vector/python-can 的 32 字节 Header + 84 字节负载读取；现有合成 CAN FD 测试验证了该路径。

## 5. LIN 与数据库设计

- `RawFrame` 与紧凑存储新增 `bus_type`，查询和时序接口接受 `can` 或 `lin`，避免 CAN 与 LIN 使用相同数值 ID 时混淆。
- `database_paths` 可同时接收多个 `.dbc`、`.arxml`、`.ldf` 文件或目录；原 `database_path` 保留兼容。
- CAN/ARXML 继续使用 cantools；LDF 使用 ldfparser，当前索引无条件帧及其信号。
- 数据库搜索结果返回 `bus_type`、`frame_id` 和 `database_file`。同一信号匹配多个数据库时不选择第一个，要求调用者明确 `database_file`。
- `decode_signal` 根据候选自身的总线类型过滤帧；MCP 层只转发参数，不承载解析或诊断逻辑。

## 6. MCP Tool 变化

Trace 新增 `get_trace_load_status`，返回阶段、扫描对象数、已索引帧数、总对象数、进度、耗时与错误。`load_trace` 改为后台加载并支持 `database_paths`；`find_messages`、`get_message_timing`、`decode_signal` 支持 `bus_type`，`decode_signal` 支持 `database_file` 消歧。

Config 新增 `get_config_load_status`，用于等待或查询工程/ARXML 后台索引状态。

两个 MCP 的 Tool 超时从 60 秒调整为 120 秒；Load 本身通常在毫秒级返回，状态 Tool 单次最多等待 55 秒，为 Harness 留出协议返回余量。

## 7. Skill 与 eval 调整

Trace、Config、Debug 三个 Skill 均明确规定：每份输入只 Load 一次，`index_ready=false` 时使用原 ID 调用状态 Tool，仍未完成只继续查询状态，不重复加载。Trace 指令新增 CAN/LIN `bus_type`、LDF 和多数据库消歧规则。

三个长期 eval 规格同步加入状态 Tool；Trace eval 新增 LIN 0x2A + LDF 信号解码场景。这些 JSON 是工程契约，不是临时测试产物。

## 8. 自动化测试

新增或更新的覆盖包括：

- python-can 生成的经典 CAN 与旧格式 CAN FD 真实 BLF 对象；
- vblf 生成的 LIN 0x2A BLF 对象、1-based Channel、DLC 与 payload；
- 最小 LDF 2.1 的信号搜索与解码；
- Trace/Config 后台 Load 立即返回、相同输入复用同一 ID、索引中查询得到明确 NotReady 错误、状态等待到 ready；
- FastMCP 进程内契约和两个真实 stdio 启动器的 Tool 集；
- 三个 Skill、插件清单和 eval 计划的一致性。

完整回归结果：`63 passed`，Ruff 检查通过，`pip check` 未发现依赖冲突。

## 9. 真实输入能力验收

本机只读输入：623.5 MB BLF、12 个 DBC、8 个 LDF 和 45 MB 明确 ARXML。文件未复制、修改或提交。

Trace：

- 首次 Load 0.026 秒返回，紧接的相同 Load 0.342 秒返回同一 `trace_id`，`reused=true`。
- 后台约 280.4 秒扫描 25,055,371 个对象并索引 16,534,358 帧。
- 摘要识别 2,015,029 帧 Classic CAN、13,746,540 帧 CAN FD、772,789 帧 LIN。
- `bus_type=can` 的 0x207 与 `bus_type=lin` 的 0x2A 均可查询；LDF 搜索返回两个 0x2A 的明确数据库候选。

Config：

- 45 MB ARXML 的首次与重复 Load 均约 0.001 秒返回同一 `workspace_id`。
- 后台约 12 秒内完成，识别 15,169 个命名对象、1,984 个 Message 和 1,296 条路由。

以上仅验证 Bug 修复和能力边界，没有解码或判断真实问题中的超时值切换，也没有形成根因结论。用户未明确提供工程源码根路径，因此本轮没有把相邻目录擅自作为源码工程进行 3,851 文件验收。

## 10. Code Review 与修复

基于最终差异审查了后台并发、ID 稳定性、stdio 退出、BLF 时间戳与 Channel、CAN FD 布局、LIN ID 冲突、数据库歧义、Tool 输出规模和文档契约。审查中已修复：

1. Config 原同步实现把状态锁覆盖到完整扫描/解析，导致不同输入的后台 Load 入口仍可能被阻塞；现已把重型构建移出状态锁并用单独信号量串行化。
2. vblf 旧 CAN FD 对象尺寸不兼容 python-can 夹具；增加局部兼容解析并通过真实二进制对象测试。
3. `bus_type` 校验后未把大小写规范化结果传给存储查询；现已返回并使用规范值。
4. Skill 如果只说“一次 Load”仍可能在索引中误用查询 Tool；现已明确状态等待、失败停止和禁止重复 Load。

未发现需要新增运行时抽象、磁盘数据库或独立模型调用的理由。

插件基础版本提升为 `0.6.0`，最终 cachebuster 版本为 `0.6.0+codex.20260910031418`。

## 11. 进程与临时目录清理

最终交付时已把用户级 Codex 配置中旧 `[mcp_servers.davinci_gateway]` 的 `enabled` 从 `true` 改为 `false`。随后精确匹配旧安装路径，终止当时残留的 24 个 `davinci-gw-mcp.exe` 进程，并删除 20 个对应的 `_MEI*` 解包目录；复核时进程与 `_MEI*` 均为 0。该用户级配置属于本机状态，不纳入 Git。

所有 pytest 与真实验收临时目录均定向到工作区外的专用目录，交付前定点删除。真实 BLF、DBC、LDF、ARXML 和任何解析缓存都不进入 Git。

## 12. 当前已知限制

- Trace/Config 索引仅在当前 MCP 进程内有效，服务重启后需要重新加载。
- 大 BLF 使用紧凑内存数组且不占大型磁盘缓存，但仍需要足够 RAM 容纳帧字段、payload 和 ID 索引。
- LDF 当前索引无条件帧；事件触发帧、诊断调度和 LIN 运行时状态机不在本轮范围。
- Config 状态当前提供阶段与耗时，不提供逐文件百分比。
- `arbitration_id` 为兼容既有 Tool 契约而保留；LIN 调用中它表示 0x00 至 0x3F 的 Frame ID。

## 13. 下一轮建议

先在禁用旧全局 `davinci_gateway` EXE 后，用新插件会话确认不再产生 `_MEI*` 与重复旧进程。若后续真实大 BLF 的内存占用仍影响使用，再基于实际峰值测量评估分块磁盘索引；本轮不提前引入数据库。对具体 CAN→LIN 超时现象的诊断应作为独立调查，由用户明确给出 Channel 映射、信号名与复现时间范围后再执行。
