# 第 3 轮开发日志：Trace Agent 插件化与只读 Tool 修复

## 1. 本轮目标

本轮把已有 Trace Agent 从“只能依赖开发仓库启动的项目级 Skill + MCP 配置”整理为可安装的 Codex Plugin，并同时完成以下事项：

- 支持 `$trace-analysis` 显式调用和自然语言隐式触发；
- 为全部 6 个 Trace MCP Tool 补充标准只读注解；
- 消除对开发仓库路径、个人 Python 路径和本机代理的硬编码；
- 继续复用已有 Miniconda 环境，不另建虚拟环境；
- 使用真实 Codex 会话验证云端模型能够调用本地 MCP；
- 根据真实工程问题清单补充标准问题描述解析规则；
- 不引入 API Key、OpenAI API Client、Agents SDK 模型运行时或 Provider 抽象。

## 2. 原生机制调研结论

Codex Plugin 是最小且可实际分发的封装方式。一个插件可以把 Skill 与 MCP Server 一起交付；`.codex-plugin/plugin.json` 描述插件，`.mcp.json` 注册 MCP，`skills/<name>/SKILL.md` 提供领域指令。仓库自身可以通过 `.agents/plugins/marketplace.json` 成为一个可添加的插件市场。

Skill 的显式与隐式入口由 Harness 原生提供：用户可显式选择 Skill，也可以让 Harness 根据 Skill 的 `description` 和 `allow_implicit_invocation` 自动匹配。本项目不需要实现命令路由器或单独调用模型。

旧的 `.agents/skills/`、`.codex/config.toml`、根目录 `scripts/` 和根目录 `src/` 已删除或迁入插件。迁移后只有插件包中保留 `trace-analysis` Skill；仓库根目录遗留的空 `skills/` 目录也已删除。

## 4. 为什么不继续使用项目级 Skill

项目级 Skill 适合在打开开发仓库时自动参与当前工程任务，但用户实际使用场景是：在任意目录或桌面会话中给出 BLF、DBC 的绝对路径和问题描述，然后开始调查。如果继续依赖开发仓库，用户每次都必须绑定该路径，无法形成独立产品。

插件安装后，Codex 从自己的插件缓存加载 Skill、MCP 配置、启动器和 Python 源码。输入文件仍由用户以绝对路径显式提供，所以调查工作不依赖开发仓库作为当前工作目录。

## 5. Python 环境与私人配置

PowerShell 启动器按以下顺序选择解释器：

1. 当前进程显式设置的 `ANDA_PYTHON`；
2. 当前用户 `%LOCALAPPDATA%\AutomotiveNetworkDebugAgent\python-path.txt`；
3. 已激活 Conda 环境中的 Python；
4. `PATH` 中的 `python`。

解释器路径属于个人机器配置，不进入 Git，也不写入插件清单。发布包不硬编码 `D:\...`、用户名、Conda 环境名或 `127.0.0.1:7890`。代理只允许由使用者在自己的网络环境中临时配置，Trace MCP 本身不需要联网。

启动器会把插件缓存内的 `src` 放入 `PYTHONPATH`，确保实际运行的是已安装插件内容，而不是碰巧存在的开发仓库 editable 路径。

## 6. 六个 Tool 的标准 MCP 注解

全部 6 个 Tool 共用同一组 `ToolAnnotations`：

- `readOnlyHint = true`：只读取 Trace/数据库并返回结果；
- `destructiveHint = false`：不破坏用户数据；
- `idempotentHint = true`：相同输入可安全重复调用；
- `openWorldHint = false`：不访问开放互联网或外部系统。

覆盖的 Tool 为 `load_trace`、`get_trace_summary`、`find_messages`、`get_message_timing`、`search_database` 和 `decode_signal`。代码中的中文注释说明了注解与审批策略的关系，避免未来添加新 Tool 时遗漏。

## 7. 上轮“本地 MCP 连不上”的真实根因

MCP Server 并未断开，Tool 也已经成功注入云端模型的工具目录。上轮原生事件中已经出现 `mcp_tool_call`，说明绑定阶段正常；失败发生在执行前审批阶段：会话设置为 `approval_policy = never`，而 Tool 没有声明只读属性，所以 Harness 拒绝执行。

本轮补充注解并在插件 `.mcp.json` 中设置 `default_tools_approval_mode = writes` 后，只读 Trace Tool 可以在禁止交互审批的验收会话中执行。模型仍可能先读取 Skill 指令，这是 Harness 使用 Skill 的正常行为，不属于一次 Trace MCP 业务调用。

## 8. 显式调用与隐式触发

显式入口使用 `$trace-analysis`（CLI）或插件界面的 Skill 选择功能。隐式入口允许用户直接描述：

~~~text
BLF：D:\logs\drive.blf
DBC：D:\logs\vehicle.dbc
问题：CAN2 为什么看不到 0x416？
~~~

`agents/openai.yaml` 明确设置 `allow_implicit_invocation: true`，Skill frontmatter 的描述包含 BLF、CAN/CAN FD、Channel、时序和信号等高辨识度触发语义。Skill 仍要求选择最短必要 Tool 路径，回答问题后立即停止。

## 9. 标准工程问题描述支持

对 `E0GA测试问题清单_测试问题清单.xlsx` 的 `测试问题清单!N1:N88` 做了只读分析：87 条数据均包含“简要描述、前提条件、操作步骤、预期结果、实际结果”；其中 37 条包含“测试路由”，33 条包含“测试网段”，另有 17 条没有显式对象标题。

问题类型主要覆盖路由未转发、周期不符合预期、超时标志/数值、路由延迟、多发/少发/过度转发、数据或类型不符、以太网转发/帧规则、网络管理/BusOff/计数器等。Skill 已按这个稳定结构提取调查对象和期望，但明确规定“实际结果”只是待验证陈述，不能替代 MCP 从 BLF/DBC 得到的证据。

## 10. DBC 解析能力确认

当前版本具备 DBC 解析能力。`load_trace` 可以同时加载 BLF 与 DBC，`search_database` 可以按 Message/Signal 名定位候选，`decode_signal` 使用数据库定义完成物理值解码。

本轮用合成 BLF 与 DBC 完成真实端到端验收：云端模型先搜索唯一的 `VehicleSpeed` 信号，再调用 `decode_signal`，得到 4 个连续物理值样本。验收文件只用于本轮测试，提交前删除，不进入工程。

ARXML 仅限 cantools 能直接读取的内容，暂未实现厂商扩展兼容层。

## 11. 真实 Harness 人工验收

在开发仓库之外的 `Downloads` 目录启动 Codex 临时会话，确认插件由安装缓存发现，MCP 的工作目录也指向插件缓存，不含开发仓库路径。

隐式用例中，模型自动选择 Trace Analysis Skill，并实际执行：

~~~text
load_trace
  → find_messages(指定 CAN2，结果 0 帧)
  → find_messages(不限 Channel，结果 CAN1 共 4 帧)
~~~

显式 `$trace-analysis` 用例中，模型实际执行：

~~~text
load_trace(BLF + DBC)
  → search_database(VehicleSpeed)
  → decode_signal(唯一候选)
~~~

两次最终回答均严格包含“现象判断、关键证据、不确定项、下一步建议”，没有把日志现象扩写成 ECU、PduR、CanIf、硬件或 CANoe 根因，也没有例行调用全部 6 个 Tool。

## 12. 插件市场命名问题与修复

初次本地安装时，市场名与插件名完全相同，导致 Codex 生成的缓存层级不符合预期。市场顶层标识改为 `shinomi-yuki`，插件仍保持 `automotive-network-debug-agent`，最终安装标识为：

~~~text
automotive-network-debug-agent@shinomi-yuki
~~~

重新添加市场和安装后，`codex plugin list` 与 `codex mcp list --json` 均能发现正确的插件与 `automotive-trace` Server。

## 13. 其他 Harness 兼容性

Codex Plugin 清单、Codex 市场索引和 `codex plugin add` 属于 Codex/ChatGPT 的原生分发机制，不能承诺被所有第三方 Harness 一键安装。

插件内部的两个核心部件可以独立复用：支持 Agent Skills 目录规范的 Harness 可读取 `SKILL.md`；支持本地 stdio MCP 的 Harness 可注册 `run_trace_mcp.ps1`。第三方 Harness 需要按自身格式完成安装和注册，但不需要 OpenAI API Key。

## 14. 桌面端与订阅边界

Codex 当前定价文档列出的可用套餐包含 Free、Go、Plus、Pro、Business、Edu 和 Enterprise；但插件在具体桌面客户端是否可见，还受客户端版本、账号功能灰度、工作区管理员策略和本地插件支持状态影响。因此不能把“非 GPT 付费订阅”简单等同于“所有桌面账号必然可安装”。

只要用户的桌面 Harness 已具备 Codex Plugin/本地 MCP 能力并允许本地进程，该插件就通过该 Harness 登录态使用云端模型，不要求单独购买 API 额度或提供 API Key。

## 15. 确定性测试覆盖

测试覆盖以下契约：

- 市场索引、插件清单和插件目录布局；
- 旧 Skill/MCP 配置目录已移除；
- 显式默认 Prompt、隐式触发元数据和四段输出规则；
- 6 个 Tool 均带标准只读注解；
- MCP 启动器从插件目录启动且不继承开发仓库 `PYTHONPATH`；
- BLF 摘要、报文查询、Channel、时序和样本上限；
- DBC 搜索、大小写规范化、信号解码及错误契约；
- 项目没有独立模型依赖或 API Key 配置。

完整回归结果为 `31 passed`；Ruff 检查通过；Plugin Validator 与 Skill Validator 均通过。Codex 原生 `codex review --uncommitted` 发现 1 个有效 P2：`pyproject.toml` 与插件清单已经发布 `0.2.0`，但 `anda.__version__` 仍为 `0.1.0`。修复后新增三处版本同步契约，并再次运行定向测试，结果为 `4 passed`，Ruff 和两个 Validator 继续通过。

修复后的插件 cachebuster 为 `0.2.0+codex.20260908015803`。当前会话占用旧缓存时，Windows 拒绝删除旧版本目录；按照插件更新规范直接执行 `codex plugin add` 后，新版本成功安装到独立缓存目录，本机状态显示 `installed, enabled`。新会话会加载该版本。

## 16. 当前限制

- 安装或升级插件后需要新建会话；旧会话的工具目录不会动态刷新。
- Codex IDE 扩展当前不能直接安装 Plugin，需要分别安装 Skill 并手工注册 MCP。
- Trace Session 与 MCP 进程同生命周期，服务重启后需要重新加载 BLF。
- 当前只支持 BLF 日志输入；DBC 已端到端验证，ARXML 受 cantools 直接解析能力限制。
- `decode_signal` 当前结果包含物理值但不单独回传数据库单位；这不影响数值解码，但回答单位问题时应把该项列为证据缺口。
- 没有 expected period、容差、路由表或软件配置时，只能报告客观现象，不能完成越界根因诊断。
