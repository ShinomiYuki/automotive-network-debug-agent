# 第 3 轮开发日志：Config Core + Config MCP

## 1. 本轮目标

本轮在已有 Automotive Network Debug Agent Plugin 内新增第二个本地 MCP Server，建立确定性的工程配置查询能力。目标链路是：

```text
工程源码 / 生成配置 + 可选的明确 ARXML
        ↓
Config Workspace
        ↓
源码符号 / Message / Signal / PDU → 配置与路由关系
        ↓
可定位的源码 / 生成配置 / ARXML 证据
```

本轮没有实现 Config Agent、Debug Agent、CANoe Agent、配置写回或完整根因诊断，也没有增加模型运行时、API Key 或 Provider 抽象。

## 2. 当前 Plugin 架构

安装单元仍然只有一个：

```text
plugins/automotive-network-debug-agent/
├── .codex-plugin/plugin.json
├── .mcp.json
├── skills/trace-analysis/
├── scripts/
│   ├── run_mcp.ps1
│   ├── run_trace_mcp.ps1
│   └── run_config_mcp.ps1
└── src/anda/
    ├── trace/
    ├── config/
    └── mcp/
        ├── trace/
        └── config/
```

`automotive-trace` 与 `automotive-config` 是两个平级、独立的 stdio MCP Server，共享 `anda` Python 包和解释器选择逻辑。Config MCP 不调用 Trace MCP。

## 3. Config Core 最终设计

Config Core 使用 Python 标准库实现，没有新增第三方依赖。工程源码是主要输入，ARXML 是确定性配置关系的可选补充：

- `config/arxml.py`：按 XML local-name 兼容 namespace URI 差异，提取标准系统描述和 DaVinci ECUC 配置关系；
- `config/models.py`：保存 Message、PDU、Frame Trigger、Routing Path 和证据位置的轻量模型；
- `config/source.py`：为 C/H/C++ 标识符建立位置、角色索引，支持源码独立 Workspace，查询时才读取有限上下文；
- `config/routing.py`：只按明确引用连接 Message、Source PDU、PduR Path 与 Destination；
- `config/workspace.py`：扫描输入、建立和复用进程内只读 Workspace，并提供业务查询入口。

MCP 层只负责 Tool 参数和返回契约，不承载 XML 解析或路由算法。

## 4. 支持的输入类型

当前支持：

- `.arxml`、`.xml`；
- `.c`、`.h`；
- `.cc`、`.cpp`、`.cxx`、`.hpp`、`.hxx`、`.inc`。

ARXML 当前覆盖三类已验证结构：

1. `CAN-FRAME-TRIGGERING`、`CAN-FRAME`、`PDU-TRIGGERING` 等 AUTOSAR 系统描述关系；
2. DaVinci/MICROSAR ECUC 的 `CanIfRxPduCfg`、`CanIfTxPduCfg`、Tx Buffer、HRH/HTH、Controller 与 `PduRRoutingPath`；
3. Com Signal/I-PDU、Signal Gateway、发送周期/模式、接收超时/替代值、I-PDU Group 及 BswM/ComM 直接引用。

未实现任意厂商私有配置的通用解释器。

## 5. Workspace 设计

`load_config_workspace` 接受工程根路径，也允许通过 `arxml_paths` 单独指定一个或多个 ARXML 文件/目录。源码工程可以不提供 ARXML 而独立加载。显式提供 `arxml_paths` 时，工程根目录中其他 ARXML 不会被自动混入，但工程目录中的 C/H 仍会完整建立索引。这用于避免多个项目或历史版本同处一层目录时被错误合并。

同一组路径在当前 MCP 进程内重复加载会复用 `workspace_id`。文件发生变化后，调用方可用 `force_reload=true` 显式重建快照。服务重启后 Workspace 不持久化。

如果用户没有说明工程路径，上层 Harness 应先要求补充。仅做源码查询时无需强制提供 ARXML；当问题需要 AUTOSAR 配置关系而用户没有说明应采用哪份 ARXML 时，Harness 必须再要求明确文件或目录，不能自行选择项目或版本。

## 6. Config MCP Tool

| Tool | 用途 |
| --- | --- |
| `load_config_workspace` | 扫描工程和明确选择的 ARXML，建立可复用索引 |
| `search_config_symbol` | 按 Message、CAN ID、PDU、配置对象或完整源码符号导航 |
| `search_source_symbol` | 搜索源码完整标识符并汇总定义/声明/引用角色 |
| `inspect_source_symbol` | 以完整源码标识符为入口，返回有限上下文和同名 ARXML 证据 |
| `trace_message_route` | 追踪 Message/CAN ID 到 Source PDU、PduR Path 与 Destination |
| `inspect_pdu` | 查看 PDU 的定义、网段、Message 和路由关联 |
| `inspect_communication` | 汇总 CanIf、Com、周期、模式、超时、替代值及源码位置 |
| `trace_signal_gateway` | 追踪 Com Signal、所在 I-PDU 与 ComGwMapping |
| `inspect_ipdu_group` | 查看 Group 成员和 BswM/ComM 直接控制引用 |
| `find_source_context` | 返回完整标识符的有限源码上下文与位置 |

所有 Tool 均声明 `readOnlyHint=true`、`destructiveHint=false`、`idempotentHint=true`、`openWorldHint=false`。

## 7. 路由追踪逻辑

标准系统描述从 CAN Frame Triggering 取得 CAN ID 与物理 Channel，再连接 CAN Frame 和 PDU。DaVinci ECUC 配置从 CanIf Rx/Tx PDU 容器取得 CAN ID、方向、DLC、ID 类型与 PDU 引用；Rx 通过 HRH，Tx 可通过直接 HTH 或 `Tx PDU → Buffer → HTH`，再沿 Controller 显式引用取得配置中的网段/控制器名称。

源码查询独立于 ARXML 工作，按完整 C/C++ 标识符返回文件、行号、保守词法角色和受限上下文。若同一完整标识符也出现在 ARXML 对象名或引用末端，则作为“同名证据”一并返回；该关系不等价于完整语义/数据流解析。

PduR 端点按每个 `ECUC-REFERENCE-VALUE` 自身的 `DEFINITION-REF` 选择 `PduRSrcPduRef` 或 `PduRDestPduRef`。实现不依赖引用在 XML 中的排列顺序，避免把 BSW Module 引用误当成 PDU。

路由不存在与 Routing Path 存在但 Destination 为空会返回不同事实。多个 Message 候选不会被猜测合并，而是返回包含 Message、网段、PDU、文件和行号的冲突说明，要求调用方补充选择条件。

## 8. 证据输出

关键结果尽量包含：

- 文件绝对路径与行号；
- ARXML 对象类型和对象名；
- XML 命名对象路径；
- AUTOSAR 引用路径；
- Source/Destination PDU；
- 生成代码或普通源码中的符号位置。

`find_source_context` 默认只返回前后 2 行，最多 5 行；单行最多 240 个字符，匹配结果最多 50 个。其他搜索和路由结果同样有固定上限，不会默认返回整份源码或 XML。

## 9. 相对初始设计的调整

- 真实 DaVinci ARXML 主要使用 ECUC CanIf/PduR 容器，而非只使用系统描述 Frame Triggering，因此新增了 ECUC 映射；
- 用户可能把多个项目文件放在同一目录，因此增加 `arxml_paths`，显式选择后不再扫描根目录中的其他 ARXML；
- Config 定位明确调整为源码/生成配置优先，并增加源码独立加载与源码符号主入口；
- 真实 Tx PDU 通过 Tx Buffer 间接引用 HTH，因此补充显式的一跳 Buffer 关联；
- 两个 PowerShell 启动器只保留薄包装，共用一个带固定模块白名单的 `run_mcp.ps1`；
- 大型 ARXML 通过流式行号扫描和逐文件 XML 解析降低峰值内存，不保留原始 XML 正文。

## 10. 性能考虑

Workspace 加载阶段只扫描和解析一次，后续查询复用内存索引。ARXML 按文件逐个解析；行号索引逐行读取，不同时保存百 MB 文本和 XML 树。源码索引只长期保存标识符位置，不保存源码正文。

在本机对一份约 106 MB 的真实 DaVinci ECUC ARXML 做只读验收，约 12 至 18 秒建立索引，识别 25,005 个命名配置对象、2,063 个 CanIf Message 绑定、1,446 条 PduR 路由和 315 条 Com Signal Gateway。该数字仅是当前机器上的开发测量，不是性能承诺。该真实文件只用于本机只读验收，未复制进仓库。

## 11. 测试

仓库内测试 Fixture 均为人工构造的最小数据，不包含真实公司工程：

- 标准 AUTOSAR CAN Frame/PDU/Channel；
- DaVinci 风格 ECUC CanIf/PduR；
- 单目标、多目标、Destination 缺失和路由不存在；
- 生成 C 配置与普通 C 源码中的重复符号；
- 无 ARXML 的源码独立 Workspace、源码符号角色和同名 ARXML 关联；
- CanIf Tx Buffer 间接 HTH、Com 属性、Signal Gateway、I-PDU Group 与直接控制引用；
- 损坏 ARXML、缺失路径、无支持文件、无效 Workspace、无结果和候选冲突；
- 两个 stdio MCP 启动器、Tool 发现、只读注解与实际调用。

此外以外部真实大文件做了人工只读验收，真实数据未复制到仓库，也不作为公开测试 Fixture。

## 12. Code Review

Codex 原生 Review 在当前宿主因外部源码传输安全策略被拒绝启动，本轮没有绕过该策略。随后按关联正确性、同名对象冲突、namespace、返回规模、只读边界和 Trace 回归等相同检查项完成本地结构化审查，并以确定性测试和真实文件只读验收复核。审查发现的问题均已列入下节并修复，最终未保留已知的高优先级缺陷。

## 13. 修复记录

开发与真实验收期间已修复：

- PduR Source/Destination 曾可能误取同容器中的第一个模块引用，改为按端点参数定义精确选择；
- Route 容器识别曾可能把嵌套 Source/Destination 也算作 Routing Path，改为要求定义路径以 `PduRRoutingPath` 结束；
- 初版读取大文件时同时保留原始文本和 XML 树，改为流式行号扫描与逐文件语法树；
- 多项目目录会产生不可区分候选，增加独立 `arxml_paths` 输入和带证据的冲突提示；
- 两个不同完整 AUTOSAR 引用可能具有相同短名，修复为不再仅凭短名跨包关联；
- 源码上下文缓存曾在命中缓存时仍重复读取文件，改为仅在首次命中文件时读取；
- DaVinci Tx PDU 经 Buffer 间接关联 HTH 时网段为空，增加显式 Buffer 引用链。

## 14. Trace 回归

使用现有 Miniconda 环境运行完整测试，最终结果为 `47 passed`。覆盖原 Trace Core、Trace MCP Contract、Trace Skill 契约、Config Core、Config MCP Contract 及两个 stdio 启动器，未发现 Config 能力导致的 Trace 回归。Ruff 静态检查、Config 相关文件格式检查、Plugin Validator 与 `git diff --check` 同样通过。

## 15. 当前限制

- 当前不是完整 AUTOSAR 通用解析器，只覆盖已验证的系统描述与 DaVinci/MICROSAR ECUC 结构；
- Workspace 仅在当前 MCP 进程内复用，文件变化需要显式 `force_reload`；
- 源码是 Config 的主要入口，但当前只做完整 C/C++ 标识符、单行词法角色和有限上下文，不解析宏展开、条件编译、跨语句数据流或完整 AST；
- Config MCP 只陈述配置和实现事实，不判断配置一定错误，也不与 Trace 事实自动合并；
- 当前没有 Config Skill/Config Agent；由 Harness 直接选择 Config MCP Tool，完整调查策略留到下一轮。

## 16. 下一轮建议

在 Config MCP 契约稳定后，再实现 Harness 原生 Config Skill，并由未来 Debug Agent 协调 Trace 与 Config 两类证据。下一轮仍应先从真实问题验收中挑选最短 Tool 路径，不应提前增加通用图数据库或模型运行时。
