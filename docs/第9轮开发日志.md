# 第 9 轮开发日志：Dynamic Verification Agent 闭环

日期：2026-09-16

## 本轮目标

在第 8 轮 Dynamic Core/MCP 基础上补齐 CANoe 实例所有权、cfg-only 网络模型、私有
Trace 释放和显式 Active Integration Smoke，并新增 Harness-native
`dynamic-verification` Skill，最小接入 `debug-analysis`。继续由 Codex/兼容 Harness 提供
模型推理，不增加 API Key、OpenAI API、Agents SDK、Provider 抽象或自定义 Subagent。

## CANoe Instance Ownership

`create_dynamic_session` 增加 `instance_mode=managed|attached`：

- `managed` 在启动前同时检查系统 CANoe 进程和 COM Running Object Table。只有确认没有
  既有实例时才允许 `py-canoe` 打开临时/影子 cfg；启动后再次确认唯一进程，并标记
  `owns_canoe_process=true`、`can_quit=true`。
- `attached` 要求系统中恰好一个 CANoe 进程且存在活动 COM 对象；必须明确指定
  offline/online，不接受 `configuration_path`，不切换模式、不添加数据库或 Offline Source。
  关闭时只释放本 Session 创建的事件接收器和 COM 引用，绝不调用 `quit()`。
- 进程、COM 或配置模式任一项无法可靠确认时保守拒绝，不猜所有权。
- 在任何 Backend/COM 创建前还要求用户明确确认有效许可证和本次占用，并传入
  `license_confirmed=true`；Skill 负责先询问，Core 负责硬拒绝未确认调用，不能从历史状态猜测。

`get_dynamic_status` 顶层稳定返回 `instance_mode`、`owns_canoe_process`、`can_quit`。
Backend 只停止由本 Session 启动的 Measurement，并继续清理由本 Session 启动的 Test、
Replay 与 Logging。

## cfg-only Network Model

`inspect_network_model` 的稳定 kind 收敛为 `database`、`node`、`message`、`signal`：

- Database 路径和 Node 直接来自当前 CANoe Configuration/Bus COM 模型；
- Message/Signal 从当前 Configuration 已加载的 DBC/ARXML/LDF 路径建立项目已有
  `NetworkDatabase` 索引，不依赖 BLF；
- 索引按数据库路径集合复用，配置加载集合变化时重建；
- 未可靠实现的 `symbol` 已从 Tool Contract、说明和 Skill 中删除。

## 私有 Trace 生命周期

`TraceSessionManager.release_trace(trace_id)` 同时移除已完成 Session、source-key 去重映射和
后台任务入口。若 release 发生在 loading 期间，任务带释放标记继续完成当前不可中断的
文件读取，但完成后丢弃局部结果，不会重新注册到 `_sessions` 或 `_source_keys`。

Dynamic 创建失败或关闭 Session 时都会释放自己的 Trace；独立 automotive-trace MCP
仍持有自己的 Manager，不受影响。实现没有引入取消框架或额外进程。

## Dynamic Verification Skill

新增插件内 `skills/dynamic-verification/`。固定调查流程为：

```text
候选假设
→ 选择 offline / attached / managed online
→ 最小 runtime policy
→ baseline
→ 一个最小刺激
→ wait_runtime_event
→ 同对象再次观察
→ 恢复 Signal/Variable
→ close_dynamic_session
→ 支持 / 削弱 / 当前无法验证
```

Skill 明确禁止猜 Raw CAN 的 Channel、CAN ID、Payload、Classic/FD、extended、BRS、次数
和间隔；不自动全开 BUS_ACTIVE；Tool 失败不编造结果；成功、失败、超时都必须 cleanup。
固定输出为“动态验证结论、实验过程、关键观察、不确定项、下一步建议”。

## Debug Agent 接入

`debug-analysis` 现在识别 Trace、Config、Dynamic 三类证据。Dynamic 不是机械第三阶段：
只有 Trace 已确认现象、Config 只给出静态期望且仍有一个明确可安全验证的运行时假设时，
才进入 `Trace/Config → Dynamic`。阶段间只新增传递单一 `runtime_hypothesis`，仍不复制大批
原始帧、ARXML 或源码。

新增 Eval 覆盖 BLF-only offline、attached 不退出用户 CANoe、Signal 与 System Variable
恢复、Raw CAN 参数缺失、最小 policy、Tool 失败不伪造、始终 cleanup，以及证据已足够时
不调用 Dynamic。Debug Eval 增加“Trace 目标端缺失 + Config 路由存在 + Dynamic 验证运行时
变量”的阶段门控用例。

## CANoe Active Integration Smoke

增加默认跳过的 `tests/integration/test_dynamic_canoe_active.py`。只有显式设置
`ANDA_CANOE_ACTIVE_SMOKE=1` 并提供 `ANDA_CANOE_SMOKE_ASSET_ROOT` 才运行；测试先把公开
演示资产复制到工作区外临时目录，再在副本中准备 Virtual CAN CAPL Bridge，不修改业务
工程。覆盖计划包括 Signal、System Variable、CAPL、Raw CAN 收发、Replay、Logging 和
Test Module；Diagnostic 只在后续具备安全模拟 ECU 时启用。

本轮实机尝试识别到 `Vector CANoe ... /pro (View Only) 14.4.13`。CANoe 明确返回
“Function is only available with valid application license”，因此 Measurement 和主动实验
无法执行；上述 Active 项与 Diagnostic 均记录为 pending，未伪造通过结果。opt-in 测试在
View Only 环境明确 skip，普通 pytest 不受影响。

## 测试与 Review

确定性测试新增/调整覆盖：

- managed/attached 状态契约和 attached close 不调用 quit；
- attached 不接收 cfg、必须明确 offline/online；
- cfg-only Message/Signal 真实数据库读取；
- Trace ready 与 loading 两种释放路径；
- Dynamic Skill、Eval、Debug 三域路由；
- 26 个 Dynamic MCP Tool 数量保持不变，只有创建参数和 kind 契约收敛。

最终执行 Dynamic Core、MCP contract、Dynamic/Debug/Trace/Config Agent 回归、stdio
launcher、完整 pytest、Ruff check、Ruff format check、Skill/Plugin 校验和
`git diff --check`。全量测试结果为 `95 passed, 2 skipped`；两项跳过均为默认关闭的真实 CANoe Active Smoke。

Review 重点结论：attached 路径没有 `quit()`；managed 不再无条件复用活动 COM；Trace
loading release 不会回驻内存；cfg-only Message/Signal 不依赖 BLF；Skill 强制 baseline、
单一刺激、恢复和 cleanup；BUS_ACTIVE 不会由默认 policy 自动开放。

## 当前限制

- CANoe Active Smoke 需要非 View Only 的有效应用许可证，本轮主机实际许可证状态未满足；
- Raw CAN Bridge 只在安全测试资产副本中准备，Core 不改写用户真实 cfg/CAPL；
- Diagnostic 仍需单独的安全模拟 ECU；
- attached 只支持能被 COM Running Object Table 唯一识别的单实例场景，多实例时保守拒绝。
