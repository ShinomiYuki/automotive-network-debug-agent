# 第 1 轮开发日志：Trace Core + Trace MCP

## 1. 本轮目标

交付可真实运行和测试的第一版 Trace Core + Trace MCP，完成 BLF 加载、Trace Session 复用、日志摘要、报文查询、时序统计和 DBC 信号解码。严格不实现 Debug Agent、Config Agent、CANoe Agent、历史案例库或机器学习能力。

## 2. 开发前现状

仓库已有 Monorepo 骨架、5 个 Trace MCP Tool 草案及少量占位测试。主要问题是 `TraceSessionManager` 通过 `list(iter_blf(...))` 长期保存每一帧 `RawFrame` 对象，大日志对象开销明显；重复加载同一 BLF 会重新解析并生成新的 `trace_id`；MCP Contract、BLF、Session、查询和 DBC 均缺少真实测试；README 不能指导使用者安装和连接。

业务输入目录已经使用 `input/`。两个参考项目仍保留在原有 `samples/` 路径，本轮未移动、删除或重构。

## 3. 社区实现参考

- `samples/MCP-CAN-main`：参考 FastMCP Server 的工具注册方式、结构化结果、参数边界，以及 CAN/DBC 业务逻辑与 MCP 层分离方式。
- `samples/bus-log-analyzer-00.01.01`（CANScope 参考源码）：参考 `BLFReaderService` 对 python-can Channel 的说明、CAN FD 字段读取，以及 `RawFrameStore` 使用紧凑列式数组避免逐帧 Python 对象常驻的思路。

只借鉴了与本轮需求直接相关的设计，没有复制 GUI、LIN、MDF、向量化解码、磁盘 mmap 或复杂兼容层。

## 4. 最终工程设计

```text
BLF --python-can--> RawFrame 流 --单次追加--> CompactFrameStore
                                              │
DBC/ARXML --cantools--> NetworkDatabase       │
                         │                    │
                         └---- TraceSession --┘
                                  │
                         TraceSessionManager
                                  │
                         5 个薄 FastMCP Tool
```

核心业务位于 `src/anda/trace/`，MCP 注册位于 `src/anda/mcp/trace/server.py`。MCP 层只转发参数和返回结果，不包含 BLF 解析、DBC 解码或时序算法。

## 5. Trace Core 数据流

`iter_blf` 使用 python-can 流式读取 BLF，每帧只在读取边界短暂构造 `RawFrame`。Session 加载过程立即把字段写入 `CompactFrameStore` 的 `array.array` 列与连续 `bytearray` payload，并按 arbitration ID 建立一份帧序号索引。查询期间不重新读取 BLF，只有真正返回的少量帧才构造成字典。

摘要在追加过程中累计 Channel、CAN ID、经典 CAN、CAN FD、error frame 和起止时间，不需要再次遍历日志。

## 6. Trace Session 设计

Session 与 MCP Server 进程同生命周期。加载键由规范化 BLF/数据库路径、文件大小和修改时间组成；输入未变化时重复 `load_trace` 返回相同 `trace_id` 和 `reused=true`。文件变化后会创建新 Session。

与原骨架相比，没有继续保留 `list[RawFrame]`，也没有引入 DuckDB、Parquet 或大型磁盘缓存。紧凑内存结构在第一版中更简单，能够显著减少对象开销，同时符合“不额外大量占用存储空间”的要求。

## 7. MCP Tool 列表

- `load_trace`：加载 BLF 及可选 DBC/ARXML，创建或复用 Session。
- `get_trace_summary`：返回起止时间、duration、总帧数、Channel、CAN ID 和 CAN/CAN FD 统计。
- `find_messages`：按 CAN ID、Channel、绝对时间范围查询原始帧。
- `get_message_timing`：返回 frame/interval count、median/mean/min/max period、max gap、标准差和相对中位数的最大绝对偏差。
- `decode_signal`：验证 CAN ID 与信号存在后解码，返回 sample count、解码错误数、min/max 和有限样本。

帧和信号样本单次最多返回 200 条。结果同时给出总数量、实际返回数量和生效上限。

## 8. 相比原设计的调整

1. 将对象列表改为进程内紧凑列式存储。原因是避免大型 BLF 的逐帧对象常驻，又不引入一期不需要的数据库和磁盘副本。
2. `find_messages` 的 CAN ID 改为可选，从而支持只按 Channel 查询；同时增加绝对时间范围。
3. `load_trace` 对未变化输入复用 `trace_id`，而不是每次随机创建并重复解析。
4. 时序结果不输出未经 expected period 支持的丢帧结论，只增加客观 jitter 指标。
5. ARXML 保留 cantools 的低成本原生支持，不增加厂商扩展修补逻辑。

## 9. Channel 决策

python-can 的 BLFReader 会把 BLF 二进制中的 1-based Channel 转为 0-based `Message.channel`。本项目在 BLF 读取边界统一加 1，对外使用 Vector/CANoe 风格的 CAN1/CAN2。转换有中文注释、真实 BLF round-trip 测试和 README 说明，不要求调用者理解库内部编号。

## 10. 测试内容

测试运行时使用 python-can 生成 225 帧合成 BLF，并用真实 DBC 通过 cantools 解码，不依赖公司日志，也没有把全部能力 mock 掉。覆盖：

- 经典 CAN、CAN FD、BRS、Channel、时间戳、DLC、payload；
- Session 加载、复用、稳定 `trace_id`、非法 ID 和缺失文件；
- 按 ID、按 Channel、limit、全局 200 条上限、时间范围、无匹配；
- 正常周期、不规则间隔、单帧和空结果；
- 正常信号、未加载数据库、不存在信号、数据库中不存在 CAN ID；
- FastMCP Tool 列表、全部 Tool 实际调用、结构化返回、错误结果和输出限制。

## 11. 测试结果

开发完成前定向 Trace + MCP 测试：21 passed。Code Review 修复并补充错误路径测试后，定向测试：23 passed。

首次运行出现的 15 个 setup error 来自已有 Conda 环境中的 `pytest-qt` 尝试访问沙箱外系统临时目录，并非业务测试失败。将 pytest 临时目录明确放到工作区并禁用与本项目无关的 pytest-qt 自动插件后，定向测试全部通过。

Code Review 修复后的最终完整回归：25 passed。`ruff check src tests`：通过。

## 12. Code Review 发现与修复

当前环境未提供可直接执行审查的原生 Code Review 工具，因此按最终实现文件进行了独立审查。审查覆盖 Channel、时间戳、CAN FD、DBC 错误、内存结构、重复解析、输出规模、死代码和测试真实性。

审查发现 `decode_signal` 为计算 min/max 暂存了目标信号的所有数值；在高频报文上会产生不必要的二次内存开销。已改为流式累计 min/max，返回值不变、额外内存变为常数级。审查同时补充了损坏 BLF 和非法 limit/Channel/时间范围测试。未发现重复 BLF 解析、MCP 超上限返回、Channel 偏移或 CAN FD 字段丢失问题。

## 13. 当前已知限制

- Session 不持久化，MCP Server 重启后需要重新解析 BLF。
- 紧凑存储仍使用内存保存必要字段和原始 payload，极大日志需要相应可用内存。
- 精确 median 时序统计会为目标 CAN ID 构造时间戳/间隔列表；它只影响单次目标报文查询，不复制整份 BLF。
- ARXML 仅支持 cantools 能直接解析的标准内容，未处理厂商私有扩展。
- 尚未基于 expected period 自动识别丢帧。

## 14. 下一轮建议

下一轮应基于真实脱敏大日志测量加载时间与峰值内存，再决定是否需要分批底层 BLF 解析或可选磁盘索引。不要在没有测量数据前提前引入 DuckDB、Parquet 或分布式方案。Trace Agent、Config/CANoe 能力也应保持为后续独立范围。
