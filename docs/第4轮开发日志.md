# 第 4 轮开发日志：Config Agent 配置调查闭环

日期：2026-09-08

## 1. 本轮目标

本轮在现有单一 `automotive-network-debug-agent` Plugin 内补齐 Config Agent 的最小可运行调查闭环。Config Agent 采用 Codex / 兼容 Harness 原生 Skill，由 Harness 提供模型推理，并自主调用本地 `automotive-config` MCP；没有实现 Python 模型运行时，也没有创建或使用 API Key。

当前闭环是：用户提供工程源码路径、可选 ARXML 路径和自然语言问题，Config Skill 选择最少的只读 Tool，最终稳定输出“配置判断、关键证据、不确定项、下一步建议”。本轮没有实现 Debug Agent，也没有把 Trace 与 Config 拼接成完整根因诊断。

## 2. 复用的 Config MCP 基础

第 3 轮已经提供统一 Config Workspace、源码索引、ARXML 对象索引和引用关系，并注册 10 个只读 Tool：

- `load_config_workspace`
- `search_config_symbol`
- `search_source_symbol`
- `inspect_source_symbol`
- `trace_message_route`
- `inspect_pdu`
- `inspect_communication`
- `trace_signal_gateway`
- `inspect_ipdu_group`
- `find_source_context`

这些 Tool 已覆盖源码定义/引用、Message/PDU 路由、CanIf/Com 属性、Signal Gateway、I-PDU Group 与 BswM/ComM 直接控制引用，因此本轮在其上实现专业调查策略，而不是为每个 AUTOSAR 参数增加一个 Tool。

## 3. Config Skill 设计

新增 `plugins/automotive-network-debug-agent/skills/config-analysis/`，其中：

- `SKILL.md` 定义输入边界、最短 Tool 路径、证据纪律、停止规则和固定输出；
- `agents/openai.yaml` 提供 Codex 展示信息、默认提示和隐式触发声明。

工程源码和 Generated Config 是主要调查对象。工程路径是必需范围，但可以位于用户机器的任意位置，不绑定插件开发仓库；ARXML 是可选补充，只在问题需要 AUTOSAR Route、CanIf、Com、Signal Gateway 或 I-PDU Group 等关系时使用。多个工程或 ARXML 版本并存时必须由用户明确选择，Skill 不自行猜测。

原 `src/anda/agents/config_agent.py` 只是独立 Python Agent 的 TODO 占位，和 Harness-native 方案冲突，已删除。Plugin 内只有一份正式 Config Skill，根目录和 `.agents/skills/` 下没有复制品。

## 4. 触发策略

显式触发使用 `$config-analysis`。隐式触发通过 `allow_implicit_invocation: true` 开启，但 frontmatter 把适用范围限定为：用户已经提供工程路径或明确配置文件，并询问静态配置或源码事实。

描述同时明确排除 BLF 现象分析、运行时状态模拟和完整根因判定，避免用户只提到“CAN”就误触发 Config 调查。Trace 与 Config 两个 Skill 的职责边界保持独立。

## 5. Tool 选择策略

每次调查只调用一次 `load_config_workspace`，后续复用同一 `workspace_id`。除非用户说明文件已经改变，否则不重复加载，也不使用 `force_reload`。

主要最短路径如下：

- 完整源码标识符：`load_config_workspace` → `inspect_source_symbol`；
- 不完整源码名称：先 `search_source_symbol`，唯一候选时再检查；
- Message/CAN ID 路由：`load_config_workspace` → `trace_message_route`；
- CanIf/Com 属性、周期或超时：`load_config_workspace` → `inspect_communication`；
- Signal Gateway：`load_config_workspace` → `trace_signal_gateway`；
- 已知 I-PDU Group：`load_config_workspace` → `inspect_ipdu_group`；
- 只知道 Message/PDU 的 Group：先 `inspect_communication` 取得规范 Group 引用，再 `inspect_ipdu_group`。

已有结果包含所需事实时立即停止，不以“全面检查”为由调用全部 Tool。

## 6. 证据纪律

Config Agent 只陈述工程源码、Generated Config 和已加载 ARXML 可以证明的静态事实。源码与 ARXML 只有在完整标识符一致或 Tool 返回显式引用时才自动关联，相似名称只能作为候选。

每项判断必须对应文件、行号、完整标识符、AUTOSAR 引用、XML 路径、参数或明确关系。“当前已加载配置中未发现”不扩大成“所有版本都不存在”；静态引用不证明规则执行顺序、运行时通信状态或实际停发。Config Agent 可以指出相关事实，但不能把它直接宣布为 PduR、CanIf、Com、ECU、硬件或 CANoe 的完整根因。

## 7. 固定输出

最终回答固定使用以下四个二级标题，并保持顺序：

1. 配置判断
2. 关键证据
3. 不确定项
4. 下一步建议

每节至少有一条内容；没有确定结论时明确写出证据边界，而不是省略章节或补造默认值。

## 8. Fixture 与验收 Case

新增 `evals/config_agent_cases.json`，作为工程内长期保留的确定性验收规格，不是临时文件。10 个 Case 覆盖：

- 路由存在；
- Routing Path 存在但指定 Destination 缺失；
- 路由不存在；
- Signal Gateway；
- Classic CAN/CAN FD、方向和长度；
- 发送周期、接收超时和替代动作；
- I-PDU Group 与 BswM/ComM 直接控制引用；
- 源码完整标识符定义和引用；
- 静态证据不足以解释运行时现象；
- Message/CAN ID 候选冲突。

每个 Case 都声明预期的最短 Tool 计划、预期事实和禁止调用的无关 Tool。确定性测试复用现有合成 Fixture；本轮没有读取或验证真实公司工程。

## 9. Harness 真实冒烟验收

本轮完成了两次全新 Codex CLI 进程验收：

- 显式调用：使用 `$config-analysis` 调查合成工程中 `0x416` 从 `SU` 到 `IC` 的路由。新会话发现已安装 Skill 与 `automotive-config` MCP，只调用 `load_config_workspace` 和 `trace_message_route`，正确输出四段结果；没有调用 Trace MCP 或其他 Config Tool。
- 隐式调用：不写 `$config-analysis`，只提供工程路径、ARXML 路径并询问 `0x534` 在 `Network_BD` 是 Classic CAN 还是 CAN FD。Harness 自动选择 Config Analysis，只调用 `load_config_workspace` 和 `inspect_communication`，返回 `STANDARD_CAN_FD`、16 字节和接收方向，并按四段结构回答。

两次 CLI 会话的 WebSocket 连接均超时后由客户端自动回退到 HTTPS 并成功完成，未使用或写入代理配置。

已有的桌面 Host 会话在安装后没有热刷新 Skill/MCP 快照，因而无法直接发现新 Config Skill。该会话随后出现的仓库内进程回退调用不计入验收结果。全新 CLI 进程能够正常发现和调用，说明插件接入有效；安装或更新后仍必须新建会话，必要时重启承载插件的桌面 Host。

## 10. Config MCP 是否修改

本轮没有修改 Config MCP 的 Tool、接口、索引或解析逻辑。

## 11. 不修改 Config MCP 的原因

现有 10 个 Tool 已能完成本轮所有合成 Fixture 的最小调查路径，返回的文件/行号、对象路径、引用和参数证据也足够驱动 Skill 形成可审查回答。当前没有发现必须通过新增 Tool 才能回答的高优先级缺口；继续拆分参数 Tool 只会增加无意义选择和上下文成本。

## 12. Token 与 Tool 调用控制

Skill 默认搜索结果上限为 20，源码上下文通常只取前后 2 至 3 行。路由或通信 Tool 已返回答案时不再补搜同一对象；候选冲突时停止并要求必要条件，不把全部候选和整个 Tool 返回倾倒进最终答案。

合成 Case 规定每条计划最多 3 次 Tool 调用，且 `load_config_workspace` 恰好一次。两次真实 Harness 冒烟各只调用 2 个 Config Tool。

## 13. Code Review

曾尝试使用 Codex 原生 review 检查未提交改动，但平台拒绝了把完整未提交 diff 发送到外部 review 会话的权限，因此没有绕过限制重试。本轮改为在当前会话执行本地结构化审查：逐项核对 Skill 触发边界、Plugin 形状、Tool 名称、固定输出、评测计划、README、版本号和禁止项。

## 14. Review 发现与修复

本地审查与真实冒烟共发现并修复：

- Plugin 默认提示原有 4 条，超过当前校验器允许的最多 3 条；合并为 3 条后通过；
- 周期/超时 Case 未限定 `Network_BD` 到 `Network_IC`，可能命中收发多候选；已补充网段；
- 候选冲突 Case 的问题语义与预期 `trace_message_route` 不完全一致；已改为明确询问 `0x534` 路由；
- Windows 控制台生成的初始 `openai.yaml` 不是有效 UTF-8；已删除该新建损坏文件并以 UTF-8 重建；
- Python Config Agent TODO 占位会误导实现形态；已删除，保留 Harness-native Skill 作为唯一 Agent 实现。

未发现需要改动 Config MCP 的问题。

## 15. 最终回归

最终回归使用本机已有 `DaVinci-GW` Conda 环境完成，所有 pytest 临时目录与 Python 缓存均定向到工作区外的专用目录。结果如下：

- Config Skill `quick_validate.py`：通过；
- Plugin `validate_plugin.py`：通过；
- `ruff check --no-cache .`：通过；
- 改动 Python 文件 `ruff format --check --no-cache`：通过；
- Config Agent、Trace Agent 与 Config MCP 契约聚焦测试：11 passed；
- 完整测试套件：52 passed，耗时 33.57 秒。

## 16. 已知限制

- 本轮只用合成 Fixture 验证静态 Config 调查，没有使用真实公司工程；
- Config 源码索引不解析宏展开、条件编译、跨语句数据流或完整 AST；
- ARXML 查询是面向已验证 AUTOSAR/DaVinci/MICROSAR 结构的确定性索引，不是完整通用解析器；
- Config Workspace 只在当前 MCP 进程内有效，文件变化或服务重启后需要重新加载；
- 当前 Config Skill 不调用 Trace MCP，不能自动联合两类证据形成完整根因；
- 安装或升级插件后，旧会话不会热加载新 Skill/MCP，必须新建会话，桌面 Host 必要时需要重启。

## 17. 下一轮建议

下一轮可在用户提供真实测试反馈、真实工程范围和明确 ARXML 版本后，先验证 Config Tool 对真实工程结构的覆盖，再设计主 Debug Agent。Debug Agent 应负责协调 Trace 与 Config 两类证据、管理调查假设和缺口，但仍由 Harness 提供模型推理，不引入 API Key、独立模型运行时或 Provider 抽象。
