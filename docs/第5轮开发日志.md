# 第 5 轮开发日志：Debug Analysis 调查闭环

## 1. 本轮目标

在现有 Trace Analysis、Config Analysis 和两个本地 MCP 基础上，交付一个可安装、无需 API Key、由 Codex / 兼容 Harness 原生推理驱动的主 Debug Analysis Skill。它需要根据自然语言问题动态选择 Trace、Config 或两者，在证据足够时停止，并固定输出“综合判断、关键证据、候选原因、不确定项、下一步建议”。

## 2. 已完成的架构调研结论

当前稳定分发契约是 Plugin 中的 Skill 与 MCP。Skill 是提供给 Harness 的专业指令，不是可由另一个 Skill 正式调用的 Tool；Plugin 当前也没有稳定的命名 Custom Subagent 分发契约。因此本轮直接使用 Harness 的模型推理和已注册 MCP Tool，不自行实现模型运行时。

## 3. 为什么采用方案 A

方案 A 的结构为 `debug-analysis → automotive-trace / automotive-config`。它完全复用现有两个只读 MCP，改动小、能够真实安装运行，并可通过 Skill 规则、Tool Description、Eval 和新会话 Smoke 验证动态调查行为。安装单元仍只有一个 Plugin。

## 4. 为什么本轮不用 Skill-to-Skill

`$trace-analysis` 与 `$config-analysis` 是面向用户的显式 Skill invocation，不是 Debug Skill 可依赖的稳定内部调用接口。Debug Skill 只保留调查规划所需的最短 Tool 用途，直接调用两个 MCP；Trace 与 Config 专业 Skill 继续作为独立入口。

## 5. 为什么不实现 Custom Subagent

本轮需要先证明单 Harness 会话内的多源证据闭环。为此引入 `.codex/agents/*.toml`、自定义 Agent Runtime 或 Python DebugAgent 会扩大范围，并不能改善当前 Plugin 的正式可分发性。本轮删除了旧的 Python DebugAgent 占位文件，没有新增 Agents SDK、API Key、Provider 或模型客户端。

## 6. Debug Skill 设计

新增 `plugins/automotive-network-debug-agent/skills/debug-analysis/`，包含 `SKILL.md` 与 `agents/openai.yaml`。frontmatter 将 Debug 限定为跨来源故障定位或明确的“为什么/定位/综合分析”，并明确纯日志事实优先 Trace、纯静态配置优先 Config。工程源码与 Generated Config 是 Config 的主要证据，ARXML 仅作为用户明确选择的补充。

Debug Skill 支持问题清单常见字段，但把“实际结果”视为待验证陈述。需要比较逻辑网段时，必须有用户明确给出的数字 Channel 映射，例如 `SU=CAN1、IC=CAN2`；不得从网段名称猜测 Channel。

## 7. 调查路由

- `Trace only`：存在性、Channel、周期、间隔、日志范围或信号值。
- `Config only`：工程源码、Generated Config、路由、通信属性、Signal Gateway、I-PDU Group 或源码标识符。
- `Trace → Config`：先用 BLF 验证运行时现象，只有现象成立且静态证据能继续缩小时进入 Config。
- `Config → Trace`：先验证用户明确怀疑的配置，只有配置未充分解释问题且已有 BLF 时进入 Trace。

第二阶段必须由第一阶段的实际结果触发，不能预先机械执行两个证据域。

## 8. 跨域信息传递

阶段间只传递 CAN ID、规范 Message/PDU/Signal 名、源/目标网段、明确 Channel 映射、时间范围、期望通信属性和已确认的存在/缺失现象。Raw Frame 列表、整份 ARXML、大段源码和整批 Tool 结果不跨域复制。

## 9. 联合证据规则

- Trace 与 Config 一致时，只使用“当前证据高度指向/支持/最可能”等有边界的措辞。
- Config 存在而 Trace 异常时，只判断实际行为与静态期望不一致，不直接认定源码 Bug。
- 当前 BLF 推翻问题单陈述时，明确指出当前日志未复现问题。
- Trace 与 Config 冲突时，不强行解释，优先检查 BLF、DBC、工程源码和 ARXML 的版本一致性。
- 证据不足时明确说明无法形成可靠候选，不为满足格式而猜根因。

## 10. 停止规则

单域已经回答问题、问题前提被推翻或联合证据已足够时立即停止。不重复 Load，不重复查询同一证据，不扩查无关 CAN ID、Signal、源码符号或 I-PDU Group。普通 Trace 样本查询固定使用 `limit=20`；指定 Channel 查询为零时，只在确需确认其他 Channel 时补一次相同范围的不限 Channel 查询。

## 11. Eval Case

新增 `evals/debug_agent_cases.json`，包含 11 个长期保留的确定性用例，覆盖 Trace only、Config only、Trace→Config、Config→Trace、输入不足、问题描述与 Trace 冲突、Trace/Config 版本冲突、Signal Gateway 和证据不足。每个跨域用例记录阶段门控条件和允许传递的有限事实；契约测试同时验证 Tool 名、禁止 Tool、顺序和每域最多一次 Load。

## 12. Harness Smoke

插件最终版本安装后，在工作区外使用合成 BLF 和仓库 Config Fixture 启动了三个全新、临时 Codex CLI 会话：

- Smoke A（Config only）：仅调用 `load_config_workspace → trace_message_route`，确认 0x416 的 SU→IC 路由存在，并在“候选原因”中说明纯事实问题不需要故障候选。
- Smoke B（Trace only）：仅调用 `load_trace → find_messages`，使用 `channel=2, limit=20`，确认合成 BLF 的 CAN2 未观察到 0x416；未调用 Config。
- Smoke C（Trace→Config）：先复用一次 `trace_id` 查询 CAN1/CAN2，得到 CAN1 五帧、CAN2 零帧；再加载一次 Config Workspace 并查询 SU→BD，确认路由路径存在但 BD Destination 缺失。最终五部分输出保持证据边界。

另外用两个不带 `$debug-analysis` 的新会话验证了触发区分：纯静态问题选择 Config Analysis，纯 BLF 问题选择 Trace Analysis，Debug 没有抢占专业 Skill。

本机到云端模型的 WebSocket 多次超时后由 Codex 自动降级为 HTTPS，两个本地 MCP 均正常启动和响应。检查时本机 7890 端口未监听，因此没有把个人代理配置写入项目或安装清单。

## 13. Tool 调用控制

Skill 中明确了典型问题的最短 Tool 路径、`limit=20`、单输入单次 Load、第二阶段结果门控和单域停止条件。最终联合 Smoke 共调用五次业务 Tool：一次 Trace Load、两次 Channel 查询、一次 Config Load、一次路由查询；没有摘要、时序、Signal、源码符号或 I-PDU Group 等无关调用。

## 14. Code Review

使用 Codex 原生 `review --uncommitted` 完成独立审查。审查重点覆盖动态路由、阶段门控、证据因果边界、Plugin 数量、MCP 数量、Skill 触发冲突和独立模型运行时禁令。审查报告提出两个有效问题：逻辑网段缺少数字 Channel 映射时无法执行 Trace 端点比较，以及跨 Channel 补查条件错误地写成了“Channel 为零”。

## 15. 修复

- Skill、README 和 Eval 统一要求在比较逻辑网段时提供明确数字 Channel 映射；缺失时询问或在问题允许时改走 Config→Trace，不猜映射。
- 将补查条件改为“指定 Channel 首次查询返回零条匹配”，并保留相同 CAN ID 和时间范围。
- 根据初次 Smoke 修正普通查询 `limit=20`，并要求纯事实问题不把事实结论重述成故障候选。
- 契约测试新增上述规则和相关 Eval 输入断言。

## 17. 当前限制

- Debug Agent 当前按方案 A 在同一 Harness 会话中直接访问两个 MCP。
- 尚未使用独立 Subagent 上下文，Tool scope 主要由 Skill、Tool Description 和 Eval 约束。
- 不模拟 BswM/ComM/Com 运行时状态，不自动修改配置，也不实现 CANoe Agent/MCP。
- 当前只完成合成 Fixture 软件闭环，尚未使用真实公司工程完成全链路验收。

## 18. 下一阶段真实工程验收建议

下一阶段不先增加功能，而是选择一个明确的真实问题，提供相互对应的真实 BLF、DBC、工程源码、明确采用的 ARXML、复现时段和网段到 CAN Channel 映射。依次验证问题前提、静态配置、跨域结论、版本一致性和下一步动作是否真正缩短人工定位时间。真实数据只在本机指定路径读取，不提交仓库。
